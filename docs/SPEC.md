# SPEC.md (Architecture & Requirements Guide)

※ ゲーム名: **Vege-Table**。ドメイン: `vegtab.app`。

## 1. プロジェクト概要

毎日出題されるデイリーパズル（3マッチ）でスコアを競うカジュアルゲーム。Wordleのように「今日の問題」を全プレイヤーが共有し、結果をSNSでシェアする体験を軸とする。

### 1.1. コアコンセプト
- **デイリーパズル:** 毎日JST 0時に新しいシード（パズル問題）が出題される。全プレイヤーが同じ盤面に挑戦する。
- **シード値固定:** シードごとに初期盤面と落下ピースの順序が完全に一致する。同じシードを何度リトライしても同じ操作で同じ結果が得られる。
- **無制限リトライ:** デイリーシードは何度でもプレイ可能。ベスト記録がランキングに反映される。
- **過去のデイリー:** カレンダーUIで過去のデイリーシードを遡ってプレイできる。
- **ゲームの目的:** 盤面に配置されたおじゃまタイルを全て除去する（クリア）。少ない手数でのクリアを競う。詳細は §3.7。
  - かつては Sprint（手数制限ハイスコア）、Survival（ウェーブ侵食からの生存）、Cascade（連鎖ポイント）のモードもあったが、#102 で撤去し、旧 Clear モードだけのゲームにした。

### 1.2. ランキングとシェア
- ランキングはシードごとに存在する。並び順は §3.7。
- HOME画面からは当日のデイリーシードのランキングにショートカットでアクセスできる。
- プレイ結果をSNS等にシェアできる。シェア内容にはシード情報・クリア/失敗・手数・クリアまでの時間を含む。
- ランキングにはプレイヤーの表示名（display_name）が表示される。載るのは名前とランキングへの公開の同意を設定した ID の記録だけ（§5.2）。
- 自分のランク（順位）がランキングモーダル上部に強調表示される。
- リプレイデータがあるエントリには再生ボタン（▶）が表示され、手順再生画面に遷移できる。ランキングの締め切り前は自分のエントリだけ、締め切り後は全エントリが対象になる。

### 1.3. ユーザー名（表示名）
- 表示名は kan-game.app の名前で、kan-game.app のゲームで共通。重複できず、一度決めると変えられない（§5.2）。
- 見た目の 2〜20 文字。規則は kan-game.app の ID 基盤が決める。
- 決めるときに、vegtab のランキングへ公開することに同意する。別のゲームで名前を決めていれば、同意だけを求める。
- HOME 画面と、ゲーム終了後の案内から設定できる。未設定のあいだ、ローカルの表示は「NO NAME」。

### 1.4. 実績（トロフィー）
- パズルプレイを通じて実績を解除できるコレクション要素。報酬なしの純粋なトロフィーシステム。
- 詳細は §3.9。

## 2. UI/UX と世界観テーマ
- **テーマ:** 「野菜」
- **タイル:** 5種類の色の異なる野菜アイコン。視認性を重視し、色だけでなくシルエットでも区別できるデザインとする。
- **アイテム:** 食器・調理器具をモチーフとする。表示名はスプーン（scope）、ハサミ（v_cut/h_cut）、食器セット（burst）、サラダボウル（flush）。詳細は §3.13 のアイテム表示名テーブルを参照。
- **おじゃまタイル:** 盤面に配置される除去対象の障害物（§3.5）。
- **画面構成:** スマートフォンに最適化。HOMEダッシュボード、パズル画面、カレンダー（過去デイリー）、ランキング。
- **ダークモード:** CSS Custom Properties によるテーマ色定義。`prefers-color-scheme` 自動検出 + 手動トグル。
- **i18n:** 日本語/英語対応。ブラウザ言語自動検出 + 手動切替。
- **アニメーション速度:** パズル画面のマッチ・消去・落下アニメーションの速度を 1x / 2x / 3x / 4x で切替可能。設定メニューから変更。localStorage保存。

## 3. パズルルール詳細

### 3.1. 盤面基本ルール
- **盤面サイズ:** 8×8の正方形
- **タイルの種類:** 5種類の野菜
- **配置決定:** シード値を元にした擬似乱数でタイルの配置と落下順序が決定される。盤面外（下方向）にも無限にタイルが並んでいるものとする。
- **初期盤面:** シード値に基づいてランダム配置した後、マッチが存在する場合は自動消去＋落下を安定状態になるまで繰り返す。この初期自動消去ではスコアは加算されず、アイテムも生成されない。自動消去完了後の盤面がプレイヤーの開始盤面となる。
- **マッチ判定:** 以下の2種類のパターンでマッチが成立し、該当するタイルが消去される。
  - **直線マッチ:** 同種のタイルが縦または横に3つ以上連続で並んでいる場合。
  - **2×2マッチ:** 同種のタイルが縦横2×2の正方形に並んでいる場合。
- **操作:** プレイヤーは隣接するタイルをスワイプで入れ替えられる。ただし、入れ替えの結果マッチが成立する場合のみ有効。
- **落下補充:** タイルが消えた後、上方のタイルが重力で落下し、空いたスペースにはシード値に基づく新しいタイルが上から補充される。落下後にマッチが発生した場合、連鎖として続けて消去される。補充タイルは列ごとに独立した擬似乱数ストリーム（シード値由来）で生成されるため、同じシードであれば各列のN番目の補充タイルは常に同じ色になる（プレイ順序に依存しない決定性）。

  - **列ストリームの独立性（重要）:** 各列のシードは avalanche ハッシュ（`mix32`）で撹拌して生成する。撹拌せずに乱数の生の状態値を列シードに流用すると、列同士が「同じストリームを数ステップずらしただけ」の関係になり、ある列が隣より1回多く補充された時点で状態が完全に一致してしまう。一致した列は以後ずっと同じ色を引くため、盤面が不自然になるうえ、消しても同じ並びが補充され続けて自動消去ループが終わらなくなる。
- **ゲーム終了条件:** 全おじゃまタイルの除去（クリア）または詰み（失敗）。詳細は §3.7。

### 3.2. アイテム生成ルール

ゲーム中に特定のパターンでタイルを消すと、その位置にアイテムが生成される。

| 消去パターン | 生成アイテム | 効果概要 |
|---|---|---|
| 2×2正方形 | スプーン | 周囲縦横4マス消去 + 任意1マス消去 |
| 横4マス直線 | ハサミ(縦) | 縦一列消去 |
| 縦4マス直線 | ハサミ(横) | 横一列消去 |
| 5マス以上連結（非直線） | 食器セット | 周囲2マス消去 |
| 縦または横5マス直線 | サラダボウル | 対象色の全消し |

**独立コンポーネントごとのアイテム生成:** 1回の操作で複数のマッチが発生した場合、色と位置が連結しているマッチ群を1つのコンポーネントとして扱い、**コンポーネントごとに独立してアイテムを生成する**。例えば、スワイプで異なる色の4マッチが2つ同時に成立した場合、ハサミが2つ生成される。同色でも位置が離れていれば別コンポーネントとなる。

**コンポーネント内の優先順位:** 1つのコンポーネント内で複数の生成条件に該当する場合、より上位のアイテムが1つだけ生成される。優先順は サラダボウル > 食器セット > ハサミ(横) = ハサミ(縦) > スプーン。ただし、2×2パターンと3直線マッチが重複した場合はスプーンが成立する。2×2パターンが4直線以上やL/T字型の5マス以上連結と重複した場合は上位アイテムが優先されスプーンは生成されない。

**生成位置:**
- プレイヤーのスワイプ操作に起因する場合 → スワイプ操作の起点位置
- アイテム効果による連鎖消去に起因する場合 → 消去されたタイル群の中央

**連鎖中の配置:**
- 1連鎖目でも2連鎖目以降（落下後のマッチ）でも、生成条件を満たしたアイテムはその連鎖ステップの消去の直後に盤面へ配置される。続く落下では、他のタイルと同じように落ちる。
- アイテムのあるマスはマッチ判定の対象にならないので、配置されたアイテムが後続の連鎖のマッチに含まれることはない。

### 3.3. アイテム起動ルール

- **起動方法:** タップ（1手消費）またはスワイプで隣接タイルと入れ替え。
- **誘爆:** アイテムの効果範囲内に別のアイテムが存在する場合、そのアイテムも連鎖的に発動する。

**各アイテムの効果:**

| アイテム | タップ / スワイプ起動 | 連鎖発動（他アイテムに巻き込まれた場合） |
|---|---|---|
| スプーン | 1手消費で起動。周囲縦横4マス（上下左右）を消去した後、ユーザーが盤上の任意の1マスを選択して消去する（選択自体は手数を消費しない）。選択したマスがアイテムの場合、そのアイテムを発動する。 | 周囲縦横4マスを消去する（ユーザー選択なし）。 |
| ハサミ(縦) | タップまたはスワイプで縦一列のタイルを全て消去 | 同左 |
| ハサミ(横) | タップまたはスワイプで横一列のタイルを全て消去 | 同左 |
| 食器セット | タップまたはスワイプで周囲2マス分のタイルを消去 | 同左 |
| サラダボウル | スワイプ時：入れ替え先のタイルと同種のタイルを盤上から全て消去。**おじゃまタイルとスワイプした場合は盤上の全おじゃまタイルの耐久値を1減少させる（耐久値0で破壊）。** タップ時：上隣から時計回り順で最初に見つかるタイルと同種のタイルを盤上から全て消去 | 誘爆された時点の盤面状態で時計回り探索を行い対象色を決定する（誘爆元アイテムの消去で周囲が空になる前の状態を使用） |

※ ハサミ(横)のアイコンは、ハサミ(縦)のアイコンを90度回転させたもの。

### 3.4. アイテム合成ルール

アイテム同士をスワイプで入れ替えた場合、特殊な合成効果が発動する。スプーンの合成では、元の位置で周囲縦横4マスの消去効果も追加で発動する。

| 組み合わせ | 効果 |
|---|---|
| スプーン + スプーン | 両方の位置で周囲縦横4マスを消去 + ユーザーが盤上の任意の3マスを選択して消去する |
| スプーン + ハサミ(縦) | スプーンの位置で周囲縦横4マスを消去 + ユーザーが選んだ任意の1マスを起点に縦一列消去 |
| スプーン + ハサミ(横) | スプーンの位置で周囲縦横4マスを消去 + ユーザーが選んだ任意の1マスを起点に横一列消去 |
| スプーン + 食器セット | スプーンの位置で周囲縦横4マスを消去 + ユーザーが選んだ任意の1マスを起点に周囲2マス消去 |
| スプーン + サラダボウル | スプーンの位置で周囲縦横4マスを消去 + サラダボウルの縦横1マス隣から時計回り順で最初に見つかるタイルと同種のタイルを盤上から全て消去 |
| ハサミ + ハサミ（縦横問わず） | スワイプ位置を基準に縦横十字に消去 |
| ハサミ(縦) + 食器セット | 縦3列を消去 |
| ハサミ(横) + 食器セット | 横3列を消去 |
| 食器セット + 食器セット | 周囲3マスを消去 |
| サラダボウル + ハサミ(縦) | 対象色の全タイルそれぞれから縦一列消去が発動 |
| サラダボウル + ハサミ(横) | 対象色の全タイルそれぞれから横一列消去が発動 |
| サラダボウル + 食器セット | 対象色の全タイルそれぞれから周囲2マス消去が発動 |
| サラダボウル + サラダボウル | 盤上のタイルを全て消去。**ただしアイテムは誘爆せず盤上に残留する。** 全消し後、アイテムはその位置に留まり、周囲の空きマスにシード値に基づく新しいタイルが降ってくる。全消しボーナス +1000点。 |

### 3.5. おじゃまタイル

- おじゃまタイルは盤上に配置される障害物である。初期盤面の自動消去の後に配置される。
- **耐久値:** 1〜3。
- **消去条件:** おじゃまタイルに隣接するタイルでマッチが発生するか、アイテムの消去範囲内に含まれると、耐久値が1減る。スプーンで直接タップした場合も耐久値が1減る。耐久値が0になるとおじゃまタイルは消滅する。
- **スワイプ移動可能:** おじゃまタイルは通常タイルと同様にスワイプで隣接タイルと入れ替えられる。ただし入れ替え自体は手数を消費せず、入れ替えた結果マッチが成立した場合のみ手数を消費する。
- **落下しない:** おじゃまタイルの下のタイルが消えても、おじゃまタイル自体は落下しない（位置が固定される）。
- **すり抜け落下:** 通常タイルはおじゃまタイルをすり抜けて落下する。おじゃまタイルは固定されたまま、その上にある通常タイルは下方の空きスペースまで貫通して落下する。おじゃまタイルが消滅した場合も同様に、上のタイルがすり抜けて落下する。
- **マッチに参加しない:** おじゃまタイルは通常タイルのマッチ判定には関与しない。
- おじゃまタイルはどの日も 16 個で、耐久値は 1 が 6 個、2 が 8 個、3 が 2 個（合計 28。`engine/src/obstacle.ts` の `OBSTACLE_DURABILITIES`）。日ごとの難しさのぶれを抑えるため（#106）。位置と、どのおじゃまタイルにどの耐久値を割り当てるかはシード値によって決定される。

### 3.6. スコア計算

スコアは表示のためのもので、順位には使わない（順位は §3.7）。

#### 3.6.1. マッチ消去（野菜タイル）

- **基礎点:** 1タイル消去 = 10点
- **連鎖倍率:** N連鎖目の消去は ×N倍。プレイヤーの操作（スワイプ/タップ）で直接消えるのが1連鎖目、落下やアイテム誘爆で自然に消えるのが2連鎖目以降。
  - アイテム効果の後に続く連鎖は「誘爆の段数 + 1」連鎖目から数える（起動したアイテム・スプーン・合成の効果を1段目とし、同じ深さの誘爆は何個でも1段）。タップ・スワイプ・スプーン・合成で共通。
- **同時消しボーナス:** 同一連鎖ステップ内で複数マッチが成立した場合、2箇所目以降は1箇所あたり +30点の固定ボーナス。

#### 3.6.2. アイテム効果

アイテムの種類によらず、効果で消えたタイル 1 枚につき 10 点とする。

- **起動したアイテムと誘爆:** `10 × 消去数 × 起動時の連鎖数`。タップ起動は 1、アイテムとのスワイプは「入れ替えで起きた連鎖の数 + 1」。誘爆したアイテムの効果も同じ連鎖数で数え、誘爆の深さによる倍率はない。
- **スプーン・合成:** 1 枚 10 点（連鎖数を掛けない）。
- **サラダボウル×おじゃまタイル:** 壊れたおじゃまタイル 1 枚につき 10 点。
- **全消しボーナス:** サラダボウル×サラダボウルの全消しは +1000 点だけで、消えたタイルの点は付かない。

**計算例:**
- 1連鎖目：3タイル消去 → 10 × 3 × 1 = 30点
- 2連鎖目：3タイル消去 → 10 × 3 × 2 = 60点
- 3連鎖目：4タイル消去 → 10 × 4 × 3 = 120点
- 1手の合計 = 210点
- ハサミ(横)をタップで起動：8タイル消去 → 10 × 8 × 1 = 80点

アイテムの種類別の基礎点と誘爆の深さによる倍率は、スコアを順位に使わないと決めたので入れない（#88 を閉じた）。

### 3.7. ゲームの流れ

- 盤上に配置されたおじゃまタイル（§3.5）を全て除去するまでの手数の少なさを競う。手数の上限はない。
- スワイプ（マッチ成立時のみ有効）とアイテムのタップ起動がそれぞれ1手としてカウントされる。連鎖・落下・誘爆は手数に含まない。スプーン起動後の任意マス選択も手数を消費しない。
- 全おじゃまタイル除去でクリア。スコアはマッチ・連鎖・アイテム効果で加算される。
- 詰み状態（有効なスワイプなし かつ アイテムなし かつ おじゃまタイル残存）になった場合はクリア失敗。
- 1ゲームの最大連鎖数を記録する（連鎖の実績 §3.9 に使う）。
- **プレイ時間:** シードごとに、その日の累計プレイ時間を数える。リトライをまたいで足し続け、クリアした時点の累計をその記録の時間とする。連鎖などのアニメーション中と、パズル画面を離れている間（別の画面、別のタブ、アプリを閉じている間）は数えない。プレイ中は経過時間を画面に表示する。時間はクライアントで測り、サーバーでは検証しない（§5.3）。累計の上限は 24 時間で、サーバーは上限を超えた値を弾かずに「時間の記録なし」として保存する。
- **ランキング:** シードごとに存在する。クリアした記録だけが載り、手数の少ない順、同じ手数ならクリアまでの時間が短い順。手数も時間も同じなら同順位。時間の記録がない記録（時間を順位に入れる前の記録）は、同じ手数の中で最後に並ぶ。スコアは順位に使わない。
  - 上手なプレイヤーはほぼ最短の手数に届き、手数だけでは差が付かない（#91 の計測）。そのため時間を 2 つ目の基準にしている。
- HOME画面の当日のデイリーパズルから、モード選択を挟まずにプレイを始める。

**撤去したモード（#102）:** Sprint（15手のハイスコア）、Survival（ウェーブ侵食）、Cascade（4色・連鎖ポイント・ネクスト表示・キラキラ野菜）を撤去した。あわせて Sprint の終了時のアイテム自動発動、Sprint / Cascade のセグメント落下（おじゃまタイルで列を区切る落下）も無くなり、落下は常にすり抜け落下（§3.5）になった。撤去したモードの記録は D1 に残っているが、API は返さない（§6）。kan-game.app への移行（#103）で捨てる。

### 3.8. シード管理

- **デイリーシード:** 日付ベースで生成され、JST 0時に更新される。全プレイヤーが同じシードに挑戦する。
- **過去のデイリーシード:** カレンダーUIで過去のデイリーシードとランキングを閲覧・プレイできる。
- **リトライ:** 全シード無制限にリトライ可能。ベスト記録のみ保持される（upsert方式）。クリア済み優先、どちらもクリアなら最少手数、同じ手数なら時間の短い方を保持する（ランキングの並びと同じ基準）。
- **シェア:** プレイ結果（クリア/失敗・手数・クリアまでの時間）をSNS等に共有できる。
- デイリーシードごとに、おじゃまタイルの配置もシード値から決定的に生成される。

### 3.9. 実績（トロフィー）

パズルプレイを通じて解除できるコレクション要素。報酬はなく、純粋なトロフィーシステムとして機能する。全16種。

**評価タイミング:**

### 3.10. 手順再生（リプレイビューア）

ベストスコアの手順を後から振り返る機能。

**リプレイログの記録:**
- プレイ中の操作（スワイプ・タップ・スプーン選択・合成）を `ReplayAction` 型の配列として記録する。
- スコア送信時にリプレイログも送信される。ベストスコア更新時のみ R2 に保存される（`replay_log_key`、キーは `replays-v2/<ID>/<seed_id>/<UUID>.json`）。
- #106 より前の盤面のリプレイは、kan-game.app への移行で捨てた（§5.4）。
- セッション途中の中断時はsessionStorageにリプレイログも保存し、復帰時に復元する。

**ReplayAction型:**
- `swap`: `{ type: 'swap', pos, dir }` — 通常のスワイプ操作
- `tap`: `{ type: 'tap', pos }` — アイテムのタップ起動
- `scope`: `{ type: 'scope', pos, targetCells }` — スプーンの直接タップ起動
- `scope_swap`: `{ type: 'scope_swap', pos, dir, targetCells }` — スワイプでスプーンを移動後に発動
- `scope_synthesis`: `{ type: 'scope_synthesis', pos1, pos2, targetCells }` — スプーン合成

**再生ビューア（`/replay/:scoreId`）:**
- ランキングモーダルのエントリに再生ボタン（▶）を表示。タップで遷移。ランキングの締め切り前は自分のエントリだけ、締め切り後は全エントリに表示する。
- エンジンの決定性を利用し、シード値 + 操作列から全中間状態を再構築する。
- トランスポートコントロール: 再生/一時停止、ステップ前進/後退、先頭/末尾へジャンプ
- スライダーで任意のステップへジャンプ可能
- 速度切替: 0.5x / 1x / 2x / 4x
- アクションリスト: 全操作の一覧、現在/次のアクションをハイライト表示
- 盤面上で次のアクションの対象セルをハイライト表示

**API:**
- `GET /api/scores/:scoreId/replay`（認証必須。ランキングの締め切り前は自分のスコアのみ、締め切り後は全員のスコア）→ `{ replayLog, seed, finalScore, displayName }`

### 3.12. オフラインリトライ

- `online` イベント検知時

## 5. 認証・セキュリティ

### 5.1. 認証方式（kan-game.app の ID）

アカウントは kan-game.app の匿名 ID である（#103）。仕様の正本は kan/game の `docs/ID_DESIGN.md` で、ここには vegtab から見た契約だけを書く。

- **資格情報:** ID 基盤が発行する、`Domain=kan-game.app` の `HttpOnly` Cookie（ES256 で署名した JWT、400 日）。画面はトークンを持たず、同一オリジンの `/api/*` に Cookie が付く。
- **発行と延長:** 画面は起動時とオフラインからの復帰時に `POST /api/id/session` を呼ぶ。Worker は `/api/id/*` を Service Binding（`ID`）で ID 基盤へそのまま中継する。
- **検証:** Worker は ID 基盤の公開鍵（`ID_PUBLIC_KEYS`）で Cookie を検証し、`sub` を `user_id` として使う。API ごとに ID 基盤へ問い合わせない。検証のコード（`backend/src/lib/id-token.ts`）と RPC の型（`id-rpc.ts`）は kan/game の `src/token.ts` と `src/rpc.ts` の写しで、書き換えない。テストベクター（`backend/test/kan-game/`）と一緒に写し直す。
- **エラー:** Cookie がない、または無効なら `401`。退会した ID の Cookie は `410 id_deleted`（`deleted_accounts` で判定）。画面は `410` で ID を捨てて新しい ID を受け取り、`401` で ID を取り直す。
- **Origin:** 状態を変えるリクエストは、`Origin` が `ALLOWED_ORIGINS` に含まれることを必須にする（Cookie は他サイトからのリクエストにも付くため）。同一オリジンの `GET` は `Origin` を省けるので、`GET` では求めない。
- **環境:** 環境ごとに Cookie 名、`iss`、公開鍵が違う（`backend/wrangler.jsonc`）。ローカルは `localhost` で kan/game の `wrangler dev` を使う。開発は `vegtab-dev.kan-game.app` で `dev.kan-game.app` を、本番は `vegtab.kan-game.app` で `kan-game.app` を使う。

### 5.2. 名前、引き継ぎ、退会

- **名前:** kan-game.app 全体で 1 つで、重複できず、変更できない。規則（2〜20 文字など）と重複の判定は ID 基盤が持つ。画面が名前と公開への同意を `POST /api/user/profile` に送り、Worker が `registerName` の RPC で登録してから、名前と同意を `profiles` に書く。別のゲームで名前を決めた ID は、名前を聞かずに同意だけを求める。
- **ランキングへの公開:** 名前と同意（`profiles`）のある ID の記録だけをランキングに載せる。同意していない ID は、自分の順位（名前を決めたら何位か）だけを見られる。
- **引き継ぎコード:** kan-game.app の ID 基盤の機能（`/api/id/transfer-codes`、8 文字、10 分、1 回限り）。入力した端末はコードを発行した ID に切り替わり、その端末がそれまで使っていた ID の記録は移らない（統合しない）。
- **復旧コードと退会:** kan-game.app のポータル（アカウント画面）にだけ置く。HOME のメニューからポータルを開く。
- **退会:** ID 基盤が `GAME_VEGTAB` の Service Binding で `GameService.deleteAccount(id)`（`backend/src/game-service.ts`）を呼ぶ。`deleted_accounts` に記録し、その ID の記録（`play_scores`、`achievements`、`push_subscriptions`、`profiles`、`legacy_claims`）と R2 のリプレイを消す。何度呼んでも同じ結果になる。退会の途中に書き込まれた行は、毎日の定期実行（`sweepDeletedAccounts`）が消す。

### 5.3. 不正対策

段階的に対策を強化する。

**初期リリース:**
- **リプレイ検証:** スコア送信時にreplay_log（操作ログ）を送信し、バックエンド側でパズルエンジンを用いてリプレイ検証を行う。シード値の固定とエンジンの決定性により、操作列からスコアを再計算し整合性を確認する。
- **レートリミット:** APIエンドポイントにレートリミットを設定。

**受け入れているリスク:**
- **翌日以降の盤面を事前に解ける:** デイリーシードは日付文字列のハッシュであり、クライアントも同じ計算をする（オフラインでも当日のパズルを始められるようにするため）。そのため、誰でも翌日以降の盤面を前日までに再現し、用意した操作列を JST 0 時の直後に送信できる。リプレイ検証は操作列を再現できるかだけを確かめるので、事前に用意した操作列を区別できない。
  - サーバーが秘密鍵で日付からシードを作り、当日 0 時以降に配布する方式を検討したが、採用していない（#92）。リトライが無制限でベストスコアだけを記録する仕様では、盤面を当日初めて知った場合でも、ソルバーで作った操作列をその日のうちに送信できる。事前に解く利得は、当日の探索時間が要らないことと、同点（同順位）の中での表示順が早いことの 2 つだけである。一方、この方式ではその日の初回プレイにオンライン接続が必要になる。
  - ランキングの競技性を上げるときは、リトライ回数の制限とシードのサーバー発行を合わせて設計する。
- **クリアまでの時間は自己申告:** 時間はクライアントが測って送る値で、リプレイ検証では確かめられない。値を書き換えて送ることも、上の事前に解く方法で準備した操作列を素早く入れることもできる。時間を順位に入れたので、事前に解く利得は表示順だけでなく順位そのものになる。プレイヤーが少ない今は受け入れている（#91）。
  - 競技性を上げるときは、サーバーがその日の開始時刻を記録する方式（その日の初回プレイにオンライン接続が要る）を、上のシードのサーバー発行と合わせて検討する。

### 5.4. vegtab.app からの移行

`vegtab.app` の旧アカウント（端末に `deviceId` と JWT を置く方式）は、`vegtab.kan-game.app` の ID へ本人が引き継ぐ。同じ Worker と D1 が両方のホストを配信する。

- **旧 URL（`LEGACY_HOST` = `vegtab.app`）:** 画面は移転の案内だけを出す（`frontend/src/legacy/`）。Worker は `/s/*` を新しい URL へ `301` で送り、`/api/health`、`/api/auth/refresh`、`/api/legacy/handoff` 以外の API に `410 moved` を返す。旧アカウントは新しく作れず、書き込みも止まる。
- **引き継ぎ:** 旧 URL の画面が、端末に残る旧トークンで `POST /api/legacy/handoff` を呼び、1 回限りのトークン（32 バイト、30 分、D1 にはハッシュだけ）を受け取る。新しい URL を `#handoff=<トークン>` 付きで開き、画面が確認を取ってから `POST /api/legacy/claim` に送る。トークンを URL のフラグメントに載せるのは、サーバーのログとリファラーに残さないため。確認を挟むのは、他人のリンクで気付かないまま記録を移されないようにするため。
- **移すもの:** 旧アカウントの `play_scores` と `achievements` を、今の ID の `user_id` に付け替える。今の ID に同じシードの記録があれば、今の ID の記録を残す。実績は進み具合の良い方にまとめる。旧アカウントの名前は `registerName` で今の ID の名前として登録し、公開への同意も引き継ぐ（旧 URL でランキングに載せていたため）。取られている名前や規則に合わない名前は登録せず、画面が名前を決め直すよう求める。今の ID に名前があれば、その名前を使う。
- **移した後:** 旧アカウントの `users` の行と、端末・トークン・購読の行を消し、`legacy_claims` に移した先を残す。同じ旧アカウントは 1 回しか引き継げない。旧 URL で再び引き継ぐと `409` になり、画面は新しい URL の引き継ぎコードを使うよう案内する。
- **引き継がれない記録:** `users` に残る旧アカウントの記録は、過去日のランキングに旧 URL の名前（未設定なら NO NAME）でそのまま載る。消すと他の参加者の順位が変わるため。
- **移さないもの:** 端末の localStorage（送信前の記録、設定、プレイ中の盤面）。オリジンが変わり、新しい URL からは読めない。
- **移行のときに捨てたもの（マイグレーション 0014）:** Clear 以外のモードの記録と、定義にない実績。リプレイはすべて（#106 で盤面の生成が変わり、旧い盤面では再生できないため）。R2 の旧リプレイ（`replays/` の下）は、バケットのライフサイクルのルールで消す。新しいリプレイは `replays-v2/` の下に置く。移行の時点でまだ締め切っていないランキング（当日と、猶予中の前日）の記録も捨てた。旧い盤面と新しい盤面の記録が混ざるため。
  - `npm run deploy` はマイグレーションを当ててから Worker を出す。そのあいだに、旧い Worker が旧い盤面の記録を書きうる。旧い Worker の記録はリプレイのキーが `replays/` で始まる。デプロイの直後に `npx wrangler d1 execute DB --env production --remote --command "DELETE FROM play_scores WHERE replay_log_key LIKE 'replays/%'"` で消す。
- **旧 URL を閉じる手順:** `vegtab.app` は route（`vegtab.app/*`）で Worker に向けており、dashboard の proxied の `AAAA 100::` が要る。閉じるときは route を設定と dashboard の両方から消し、`AAAA 100::` を消す。旧 URL を残すあいだは、どちらも消さない。閉じたら、`users`・`user_devices`・`transfer_codes`・`refresh_token_families`・`legacy_handoffs` と JWT の秘密鍵（`JWT_SECRET`）、`/api/auth/refresh` と `/api/legacy/handoff` を外せる。閉じる時期は未定。

## 6. データベース設計 (Cloudflare D1)

各テーブルの `user_id` は kan-game.app の ID（§5.1）。`vegtab.app` から引き継がれていない旧アカウントの行だけは、`users.id` を指す（§5.4）。

- **`profiles`**: `account_id` (kan-game.app の ID), `display_name` (ID 基盤に登録した名前の写し), `consented_at` (ランキングへの公開に同意した時刻、ミリ秒) — ランキングに載る ID
- **`deleted_accounts`**: `account_id`, `deleted_at` (ミリ秒) — 退会した ID。Cookie は最長 400 日有効なので残し続ける
- **`legacy_handoffs`**: `token_hash` (SHA-256), `user_id` (旧アカウント), `expires_at` (ミリ秒) — 旧 URL から新しい URL へ渡す 1 回限りのトークン
- **`legacy_claims`**: `legacy_user_id`, `account_id`, `claimed_at` (ミリ秒) — 引き継いだ旧アカウントと移した先
- **`users`**: `id` (UUID), `display_name` (表示名, 最大 20 文字), `device_id`, `created_at` — `vegtab.app` の旧アカウント。引き継ぐと消える
- **`user_devices`** / **`transfer_codes`** / **`refresh_token_families`**: 旧アカウントの端末、引き継ぎコード、リフレッシュトークン。旧 URL を閉じたら捨てる
- **`puzzle_seeds`**: `seed_id`, `seed_value` (ユニーク), `share_code` (ユニーク, 6〜8文字の英数字), `daily_date` (YYYY-MM-DD), `created_at`
- **`play_scores`**: `id`, `user_id`, `seed_id`, `mode`, `score`, `move_count` (実際の手数), `move_limit` (nullable), `is_cleared` (クリア可否), `clear_time_ms` (クリアまでのその日の累計時間。ミリ秒、自己申告。未クリアと、時間を順位に入れる前の記録は NULL), `max_chain` (最大連鎖数, default 0), `cascade_points` (default 0), `replay_log_key` (R2のオブジェクトキー), `created_at`
  - `mode` に書くのは `clear` だけ。撤去したモード（sprint / survival / cascade）の行が残っているので、照会は全て `mode = 'clear'` で絞る。API の `mode` も `clear` だけを受け付ける。
  - `move_limit` と `cascade_points` は撤去したモード（Sprint / Cascade）用の列で、今は書かない（既定値のまま）。
  - 撤去したモードの行は、kan-game.app への移行（#103、マイグレーション 0014）で捨てた。不要な列（`mode`、`move_limit`、`cascade_points`）を消すマイグレーションは、コードの対応をデプロイした後に別で行う。
- **`achievements`**: `id`, `user_id`, `achievement_type`, `current_value`, `is_unlocked`, `unlocked_at`

### Phase 1: Core Engine (`engine/`)

UIを持たない、純粋なTypeScriptによる3マッチエンジンの開発。

**入力:** 盤面サイズ(8×8)、タイル種数(5、Cascadeは4)、シード値、ゲームモード（sprint/clear/survival/cascade）、モード固有パラメータ（Sprint/Cascade: 手数制限 / Survival: ウェーブ設定 / Cascade: 色数）、操作列（スワイプ/タップの座標と方向 + スプーンの選択マス）
**出力:** 各操作後の盤面状態、生成されたアイテム、連鎖情報、累計スコア、現在手数、おじゃまタイル状態、Survivalウェーブ状態（現在のウェーブ番号・次のウェーブまでの残ターン・予告位置）、Cascade CP/最大連鎖数、ゲーム終了判定

**実装する機能:**
1. シード値による決定的な盤面生成（初期自動消去を含む、スコア0・アイテム生成なし）
2. マッチ判定（縦横3以上の直線検出 + 2×2正方形検出）
3. 落下補充処理（重力 + 列ごと独立RNGストリームによる決定的タイル供給、Clear/Survivalモードではおじゃまタイルをすり抜けて落下）
4. 連鎖処理（落下後の再マッチ判定ループ）
5. アイテム生成判定（パターン認識と優先順位、2×2と直線の重複判定を含む）
6. アイテム起動・誘爆処理（スプーンの周囲4マス消去 + ユーザー選択マス消去、連鎖時は周囲4マスのみ）
7. アイテム合成処理（全パターン、スプーン合成時の周囲4マス追加消去を含む）
8. サラダボウル×サラダボウル全消し時のアイテム残留＋再補充
9. おじゃまタイル処理（Clear: シード値による配置生成 / Survival: ウェーブ制侵食。耐久値管理、消去判定、非落下挙動）
10. スコア計算（基礎点 × 連鎖倍率 + 同時消しボーナス + アイテム効果点 + 全消しボーナス + 残存アイテム自動発動）
11. 手数カウント（スワイプ・タップ操作を1手としてカウント、連鎖・落下・誘爆・スプーンの選択は含まない）
12. ゲーム終了判定（Sprint: 規定手数到達 or 詰み / Clear: 全おじゃまタイル除去 or 詰み / Survival: おじゃまタイル耐久値4到達 or 詰み / Cascade: 規定手数到達 or 詰み）
13. Survivalウェーブ処理（Nターン経過ごとにシード×ウェーブ番号から決定論的に侵食位置を算出、アイテム強制発動→おじゃまタイル設置、予告マーカー管理）
14. Cascadeモード対応（4色盤面生成、CPスコアリング、ネクストタイルプレビュー生成）

**テスト:** Vitestを用いた単体テスト。各機能に対して正常系・境界値・エッジケースのテストを記述。特にシード値の決定性（同一シード・同一操作で常に同一結果）を検証するテストを必須とする。

- **ウェーブ制侵食** — シード値とウェーブ番号から決定論的に算出した位置へおじゃまタイル（耐久値1）を設置。3ターンごとに発生、侵食個数は 12 → 16 → 20 と増加（最大20個）。
- **予告マーカー** — 次ウェーブの2ターン前から侵食予定位置を盤面上に表示。
- **強制発動** — 侵食位置にアイテムがある場合は発動してからおじゃまタイルを設置。走査順は行×列昇順で決定論的。
- **耐久値の積み上げ** — 既存のおじゃまタイルへの再侵食は耐久値+1。耐久値4到達で即ゲームオーバー。
- **重力:** Clearモード同様 `passThroughObstacles=true`（非おじゃまタイルがおじゃまをすり抜けて下詰め）。
- **ランキング・実績:** 既存のルール維持（到達手数降順、同手数ならスコア降順）。旧「区間ノルマ」用のi18nキー（`survivalQuota*` 等）は廃止し、ウェーブ情報表示用キー（`survivalWave*` 等）を追加する。
