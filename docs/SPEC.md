# Project Tomado: AGENTS.md (Architecture & Requirements Guide)

## 1. プロジェクト概要
**Project Tomado** は、「TODO管理」と「3マッチパズル」を融合させたゲーミフィケーションアプリである。
名前の由来は `todo` + `match` の組み合わせであり、同時に「ポモドーロ・テクニック（トマト）」を連想させるタスク管理の親和性を意図している。
プレイヤーは現実のTODOを消化することでパズルのスタミナやアイテムを獲得し、固定シードのパズルで純粋な思考力によるハイスコアを競う。

### 1.1. コアゲームサイクル
- **TODOとスタミナ:** TODOタスクを完了するとゲームのスタミナが回復する（1日最大5回）。時間経過による自動回復も併用する（詳細は §4.9）。
- **TODOとアイテム:** TODO完了数に応じてアイテム入手の権利を得る（詳細は §4.5）。
- **TODOとUndo:** TODO完了で1日最大1つUndoチケットを獲得する（詳細は §4.6）。
- **シード値固定と無限リトライ:** ステージごとにシード値が固定されており、初期盤面と落下ピースの順序は全プレイヤーで完全に一致する。アンロック済みのシードは無制限にリトライ可能。
- **シードの入手と共有:** スタミナ1消費でユニークなシードを生成、SNS等でスコアとセットで共有可能。共有されたシードは1回無料でお試しプレイでき、プレイ後にスタミナ1消費でアンロック（スコアをランキングに反映）するか選択できる（詳細は §4.7）。
- **デイリーシード:** 日付ベースで生成され、UTC 0時に更新。スタミナ不要で全プレイヤーが挑戦・リトライ可能。過去のデイリーシードはカレンダーUIで閲覧でき、共有シードと同じ扱いで遊べる。
- **ランキング:** シード値ごとにリーダーボードが存在する。HOME画面からは当日のデイリーシードのランキングにショートカットでアクセスできる。持ち込みアイテムを使用したプレイは参考記録扱いとなりランキング集計から除外される。ただしアイテム使用の有無に関わらず「クリア」ステータスは記録され、個人の実績（トロフィー）解除には反映される。
- **実績（トロフィー）:** TODO消化やパズルプレイを通じて最大100種の実績を解除できる。10個解除ごとにアイテム報酬を獲得（詳細は §4.10）。

## 2. UI/UX と世界観テーマ
- **テーマ:** 「デスクワーク・仕事部屋」
- **ピース（ブロック）:** 5色の「付箋」。3つ揃うと「チェックマーク（✓）」が浮かんでタスクが消化される（消える）演出。
- **アイテム:** オフィスツールをモチーフとする（はさみ、カッター、クリップ、コーヒーカップ）。
- **画面構成:** スマートフォンに最適化された3画面（HOMEダッシュボード、TODOリスト、パズル画面）。パズル画面の背景は有孔ボード（ペグボード）風を想定。

## 3. TODO機能詳細

### 3.1. タスク構造

- **タイトル:** 必須。タスクの主要な内容。
- **メモ:** 任意。備考的な補足情報。UIではタイトルを主体とし、メモは展開・表示する形式とする。
- **締切日:** 任意。日付のみ（時刻なし）。
- **サブタスク:** 任意。チェックボックス付きのシンプルなリスト形式（テキスト＋完了フラグ）。サブタスクのネストは不可。

### 3.2. タスクの完了

- 親タスクの「Done」操作がゲーム上の「TODO完了1回」としてカウントされる。サブタスクの個別チェックはカウントに影響しない。
- サブタスクが未完了の状態でも親タスクをDoneにできる。サブタスクはあくまで作業整理のための補助機能である。
- TODO完了時、以下のゲーム報酬が処理される:
  - スタミナ回復（1日最大5回まで）
  - Undoチケット獲得（1日最大1つ、ストック上限10）
  - 日次完了カウントの加算（アイテム入手権利の判定に使用）

### 3.3. グループ（フォルダ方式）

- TODOを最大5つのグループに分類できる。各グループは名前と色を持つ。
- 色はパズルの付箋5色に対応させ、世界観を統一する（「デスクの付箋を色で分類する」イメージ）。
- 1つのTODOは1つのグループに所属する。グループ未設定のTODOも許容する。
- TODOリスト画面ではグループごとに折りたたみ表示が可能。

### 3.4. 繰り返しタスク

- 固定間隔型の繰り返しルールを設定できる。
- 対応する間隔: **毎日** / **毎週**（曜日指定）/ **毎月**（日付指定）
- 繰り返しタスクを完了すると、ルールに基づく次の日付で同タスクが自動的に再出現する。
- 完了起点型（完了日から○日後）は将来拡張として検討。

### 3.5. ゲーム連動まとめ

TODO完了はゲームの以下の3つのリソースに影響する。いずれも日次（UTC 0時リセット）でカウントされる。

| リソース | 条件 | 上限 |
|---|---|---|
| スタミナ回復 | TODO 1件完了ごとに回復 | 1日5回 |
| Undoチケット | TODO 1件完了で1つ獲得 | 1日1つ（ストック上限10） |
| アイテム入手権利 | TODO 3件完了で権利発生、4件・5件で選択肢拡大 | 1日1回選択 |

## 4. パズルルール詳細

### 4.1. 盤面基本ルール
- **盤面サイズ:** 8×8の正方形
- **付箋の種類:** 5色
- **配置決定:** シード値を元にした擬似乱数で付箋の配置と落下順序が決定される。盤面外（下方向）にも無限に付箋が並んでいるものとする。
- **初期盤面:** シード値に基づいてランダム配置した後、3マッチが存在する場合は自動消去＋落下を安定状態になるまで繰り返す。この初期自動消去ではスコアは加算されず、アイテムも生成されない。自動消去完了後の盤面がプレイヤーの開始盤面となる。
- **マッチ判定:** 同色の付箋が縦または横に3つ以上連続で並んでいる場合に消去される。
- **操作:** プレイヤーは隣接する付箋をスワイプで入れ替えられる。ただし、入れ替えの結果マッチが成立する場合のみ有効。
- **落下補充:** 付箋が消えた後、上方の付箋が重力で落下し、空いたスペースにはシード値に基づく新しい付箋が上から補充される。落下後にマッチが発生した場合、連鎖として続けて消去される。
- **ゲーム終了条件:** 有効なスワイプが存在せず、かつ盤上に起動可能なアイテムも存在しない状態になったら終了。その時点のスコアが最終スコアとなる。

### 4.2. アイテム生成ルール

ゲーム中に特定のパターンで付箋を消すと、その位置にアイテムが生成される。

| 消去パターン | 生成アイテム | モチーフ |
|---|---|---|
| 横4マス直線 | はさみ | 縦一列消去 |
| 縦4マス直線 | カッター | 横一列消去 |
| 5マス以上連結（非直線） | クリップ | 周囲2マス消去 |
| 縦または横5マス直線 | コーヒーカップ | 対象色の全消し |

**優先順位:** 複数の生成条件に同時に該当する場合、より上位のアイテムが1つだけ生成される。優先順は コーヒーカップ > クリップ > カッター = はさみ。

**生成位置:**
- プレイヤーのスワイプ操作に起因する場合 → スワイプ操作の起点位置
- アイテム効果による連鎖消去に起因する場合 → 消去されたタイル群の中央

### 4.3. アイテム起動ルール

- **起動方法:** タップ（1手消費）またはスワイプで隣接タイルと入れ替え。
- **誘爆:** アイテムの効果範囲内に別のアイテムが存在する場合、そのアイテムも連鎖的に発動する。

**各アイテムの効果:**

| アイテム | 効果 |
|---|---|
| はさみ | タップまたはスワイプで縦一列の付箋を全て消去 |
| カッター | タップまたはスワイプで横一列の付箋を全て消去 |
| クリップ | タップまたはスワイプで周囲2マス分の付箋を消去 |
| コーヒーカップ | スワイプ時：入れ替え先の付箋と同色の付箋を盤上から全て消去。タップ時・連鎖発動時：上隣から時計回り順で最初に見つかる付箋と同色の付箋を盤上から全て消去 |

### 4.4. アイテム合成ルール

アイテム同士をスワイプで入れ替えた場合、特殊な合成効果が発動する。

| 組み合わせ | 効果 |
|---|---|
| はさみ + はさみ / はさみ + カッター / カッター + カッター | スワイプ位置を基準に縦横十字に消去 |
| はさみ + クリップ | 縦3列を消去 |
| カッター + クリップ | 横3列を消去 |
| クリップ + クリップ | 周囲4マスを消去 |
| コーヒー + はさみ | 対象色の全タイルそれぞれから縦一列消去が発動 |
| コーヒー + カッター | 対象色の全タイルそれぞれから横一列消去が発動 |
| コーヒー + クリップ | 対象色の全タイルそれぞれから周囲2マス消去が発動 |
| コーヒー + コーヒー | 盤上の付箋を全て消去。**ただしアイテムは誘爆せず盤上に残留する。** 全消し後、アイテムはその位置に留まり、周囲の空きマスにシード値に基づく新しい付箋が降ってくる。全消しボーナス +1000点。 |

### 4.5. アイテム持ち込みルール

- パズル開始前に、手持ちのアイテムを各種最大1個まで持ち込むことができる。
- 持ち込みアイテムは、初期盤面上の好きな位置に配置する。配置した位置の付箋はアイテムに置き換わる。
- **持ち込みアイテムを使用したプレイはランキング除外（参考記録）。** ゲーム内で生成されたアイテムの使用はランキングに影響しない。

**アイテム入手方法（TODO報酬）:**

その日のTODO完了数に応じて、アイテムを1つ入手する権利を得る。権利発生後、プレイヤーは自分のタイミングで獲得するアイテムを選択する。選んだ時点で即座に入手し、その日の権利は消費される。その日のうちに選ばなかった場合、権利は消滅する。

| TODO完了数 | 選択可能アイテム |
|---|---|
| 3個 | はさみ / カッター |
| 4個 | はさみ / カッター / クリップ |
| 5個 | はさみ / カッター / クリップ / コーヒーカップ |

**アイテムストック:** 各種類ごとに所持上限なし。複数日にわたって異なる種類を貯めることが可能。

### 4.6. Undo

- TODO完了で1日最大1つUndoチケットを獲得する。
- ストック上限は10個。上限時に獲得しても増えない。
- ゲーム中、1プレイにつき最大1回使用可能。使用すると1手前の局面に戻る。
- **Undoを使用してもランキング対象のまま。**

### 4.7. シード管理とシェア

シードには3つの入手経路があり、それぞれアンロック状態とランキング反映ルールが異なる。

| 入手経路 | スタミナ | リトライ | ランキング反映 |
|---|---|---|---|
| デイリーシード（当日） | 不要 | 無制限 | 反映 |
| 自分で生成 | 1消費 | 無制限 | 反映 |
| 共有/過去デイリー（未アンロック） | 不要 | 1回のみ | アンロック時のみ反映 |
| 共有/過去デイリー（アンロック後） | 1消費 | 無制限 | 反映 |

**シードの生成:**
- スタミナを1消費して、サーバー側でユニークなシード値を生成する。過去に生成されたことのないシード値が必ず返される。
- 生成したシードは即座にアンロック状態となり、無制限にリトライ可能。

**シードの共有:**
- プレイ結果（スコア）とセットでシードをSNS等に共有できる。
- 共有を受けた側は、スタミナ不要で1回だけお試しプレイが可能。
- お試しプレイ後、スタミナを1消費してアンロックするか選択できる。アンロックするとそのプレイのスコアがランキングに反映され、以降は無制限にリトライ可能。アンロックしなければスコアは記録されず破棄される。

**共有の導線:**
- スコア画面で「共有」を実行すると、共有URL・シリアルコード・QRコードが表示される。
- **共有URL** (`https://tomado.app/s/{seed_id}`): Cloudflare Workersで処理。SNSクローラーにはOGPメタタグ（アプリ紹介＋スコア情報）を返し、ブラウザアクセスにはアプリ紹介ページを返す。PCブラウザの場合はページ内にQRコードを表示し、スマホでスキャンしてアプリに遷移できるようにする。アプリインストール済みのスマホではディープリンク（iOS: Universal Links / Android: App Links）でアプリ内の該当シードに直接遷移する。未インストール時はストアへ誘導。
- **シリアルコード**: シードを短い英数字コード（6〜8文字）で表現。アプリ内の入力欄から手打ちで共有シードにアクセスできる。LINEやDM等、OGPが表示されない環境でのテキスト共有に有効。
- **QRコード**: アプリ内のスコア画面に表示。主に対面での共有（画面を直接見せて相手にスキャンしてもらう）用途。

**過去のデイリーシード:**
- カレンダーUIで過去のデイリーシードとランキングを閲覧できる。
- 自分が参加していない過去のデイリーシードは、共有シードと同じ扱い（1回無料お試し＋アンロック選択）。

### 4.8. スコア計算（暫定・要バランス調整）

- **基礎点:** 1タイル消去 = 10点
- **連鎖倍率:** N連鎖目の消去は ×N倍。プレイヤーの操作（スワイプ/タップ）で直接消えるのが1連鎖目、落下やアイテム誘爆で自然に消えるのが2連鎖目以降。
- **同時消しボーナス:** 同一連鎖ステップ内で複数マッチが成立した場合、2箇所目以降は1箇所あたり +30点の固定ボーナス。
- **全消しボーナス:** コーヒー×コーヒーの全消し時 +1000点。

**計算例:**
- 1連鎖目：3タイル消去 → 10 × 3 × 1 = 30点
- 2連鎖目：3タイル消去 → 10 × 3 × 2 = 60点
- 3連鎖目：4タイル消去 → 10 × 4 × 3 = 120点
- 1手の合計 = 210点

※ 数値はプレイテストを経て調整する前提の仮値。

### 4.9. スタミナ（暫定・要バランス調整）

- **最大値:** 5
- **時間回復:** 30分で1回復。最大値を超えては回復しない。
- **TODO回復:** TODO完了1件につきスタミナ1回復（1日最大5回）。最大値を超えては回復しない。
- **消費:** シード生成に1、共有/過去デイリーシードのアンロックに1。

※ 数値はプレイテストを経て調整する前提の仮値。

### 4.10. 実績（トロフィー）

事前に最大100種の実績を定義し、条件を達成すると解除される。

**実績カテゴリ（例）:**
- **TODO系:** 累計N件完了、N日連続TODO完了 等
- **パズル系:** N連鎖達成、ノーアイテムクリア、ハイスコアN点以上 等
- **コレクション系:** N種のシードをクリア、全アイテム種を1ゲームで生成 等

**可視性:**
- 大半の実績は未解除の状態でも条件が表示される（プレイヤーが狙える）。
- 一部は「秘密の実績」として条件が隠され、解除時に初めて内容が明かされる。

**報酬:**
実績を10個解除するごとに、段階的にアイテム報酬を獲得する。

| 解除数 | 報酬 |
|---|---|
| 10個 | はさみ ×1 |
| 20個 | カッター ×1 |
| 30個 | クリップ ×1 |
| 40個 | コーヒーカップ ×1 |
| 50個以降（10個刻み） | コーヒーカップ ×1 + スタミナ1回復 |

※ 実績の具体的なリストと条件値はPhase 2以降で定義する。

## 5. 技術スタックとアーキテクチャ

初期は高速なWeb開発（SPA）として進め、最終的にCapacitorを用いてiOS/Androidアプリとしてビルド・配信、およびマネタイズ（広告・買い切り課金）を行う。

### 5.1. リポジトリ構成

モノレポ構成を採用する。

```
tomado/
├── engine/             # パズルエンジン（純粋TypeScript、フレームワーク非依存）
├── frontend/           # Vue.js SPA
├── backend/            # Cloudflare Workers API
├── package.json        # ワークスペース設定
└── CLAUDE.md
```

### 5.2. フロントエンド
- **フレームワーク:** Vue.js (Composition API, `<script setup>`)
- **状態管理:** Pinia
- **タッチ操作最適化:** VueUse (`usePointerSwipe`等) を活用。パズル盤面には `touch-action: none;` を適用しブラウザ標準のスワイプ挙動を無効化。描画パフォーマンス最適化のため、アニメーションは必ず `transform` を使用する。
- **テスト:** Vitest（単体テスト）
- **ハイブリッド化:** Capacitor (初期はWebモードで開発し、フェーズ後期でネイティブ連携を実装)

### 5.3. バックエンド & インフラ
- **プラットフォーム:** Cloudflare Workers (TypeScript)
- **データベース:** Cloudflare D1 (SQLiteベースのRDBMS)
- **キャッシュ/KVS:** Cloudflare KV (デイリーシードやランキングデータの高速配信)
- **オブジェクトストレージ:** Cloudflare R2（replay_log等の大容量データ保存）

### 5.4. パズルエンジン (`engine/`)
- 純粋なTypeScriptで実装し、UIやネットワークに一切依存しない。
- 盤面生成、マッチ判定、落下処理、連鎖、アイテム生成・起動・合成、スコア計算を全て純粋関数として提供する。
- シード値を入力として与えた場合に完全に決定的な結果を返すことを保証する。
- フロントエンド（ゲームUI）とバックエンド（リプレイ検証）の双方から利用される。

## 6. 認証・セキュリティ

Capacitor（WebView）特有のCookieブロック問題を回避するため、以下の認証フローを採用する。

### 6.1. 認証方式
- **方式:** JWT (JSON Web Token) による認証。リクエストの `Authorization: Bearer <token>` ヘッダで送信。
- **トークン管理:** アクセストークン（短命）とリフレッシュトークン（長命）の2トークン方式。
- **永続化:** `localStorage` は使用せず、Capacitor公式の `@capacitor/preferences` を使用する。
- **匿名ログインフロー:** 初回起動時にクライアント側でUUIDを生成、バックエンドに送信して「ゲストユーザー」としてD1に登録。摩擦のないオンボーディングを実現する。
- **アカウント引き継ぎ:** 将来的にSNS連携等でのデバイス移行をサポート予定。

### 6.2. 不正対策

段階的に対策を強化する。

**Phase 3（初期リリース）:**
- **リプレイ検証:** スコア送信時にreplay_log（操作ログ）を送信し、バックエンド側でパズルエンジンを用いてリプレイ検証を行う。シード値の固定とエンジンの決定性により、操作列からスコアを再計算し整合性を確認する。
- **レートリミット:** APIエンドポイントにレートリミットを設定し、短時間に異常な数のTODO完了・スコア送信等を弾く。Cloudflare Workers の機能で実装。

**Phase 4（ネイティブ化以降）:**
- **デバイス認証:** Apple App Attest (iOS) / Google Play Integrity API (Android) を導入し、リクエスト元が正規アプリであることを検証する。Capacitorプラグインで対応。

## 7. データベース設計 (Cloudflare D1)

過度なJOINを避けるため、サブタスクやログはJSONを活用する。

- **`users`**: `id` (UUID), `device_id`, `is_premium` (広告除去済=1), `stamina`, `last_stamina_recover_at`, `undo_stock` (上限10)
- **`todo_groups`**: `id`, `user_id`, `name`, `color` (付箋5色のいずれか), `sort_order`
- **`todos`**: `id`, `user_id`, `group_id` (nullable, todo_groups.id), `title`, `memo` (任意の備考テキスト), `due_date`, `recurrence_rule` (null / daily / weekly:曜日 / monthly:日), `status` (active / done), `subtasks` (JSON: `[{"text": "...", "done": bool}]`), `completed_at`
- **`stamina_recovery_logs`**: `id`, `user_id`, `target_date` (YYYY-MM-DD), `recovered_count` (上限5回の管理)
- **`daily_todo_progress`**: `id`, `user_id`, `target_date` (YYYY-MM-DD), `completed_count`, `item_claimed` (0/1), `undo_claimed` (0/1)
- **`user_items`**: `id`, `user_id`, `item_type` (scissors/cutter/clip/coffee), `quantity`
- **`puzzle_seeds`**: `seed_id`, `seed_value` (ユニーク), `share_code` (ユニーク, 6〜8文字の英数字), `created_by_user_id` (nullable, 生成したユーザー), `is_daily`, `daily_date` (YYYY-MM-DD, デイリーシードの場合), `created_at`
- **`user_unlocked_seeds`**: `id`, `user_id`, `seed_id`, `unlocked_at` (アンロック状態の管理。デイリー当日分は暗黙的にアンロック扱い)
- **`play_scores`**: `id`, `user_id`, `seed_id`, `score`, `is_cleared`, `used_brought_items` (持ち込みアイテム使用=1でランキング除外), `used_undo` (0/1), `is_trial` (未アンロックのお試しプレイ=1、ランキング除外), `replay_log_key` (R2のオブジェクトキー)
- **`achievements`**: `id`, `user_id`, `achievement_type`, `current_value`, `is_unlocked`, `unlocked_at`
- **`achievement_milestones`**: `id`, `user_id`, `threshold` (10/20/30/.../100), `reward_claimed` (0/1), `claimed_at` (10個刻みの報酬受取管理)

## 8. AIエージェント向け 開発フェーズ指示

エージェントは以下のステップに従い、段階的かつテスト駆動で実装を進めること。

### Phase 1: Core Engine (`engine/`)

UIを持たない、純粋なTypeScriptによる3マッチエンジンの開発。

**入力:** 盤面サイズ(8×8)、付箋色数(5)、シード値、操作列（スワイプ/タップの座標と方向）
**出力:** 各操作後の盤面状態、生成されたアイテム、連鎖情報、累計スコア、ゲーム終了判定

**実装する機能:**
1. シード値による決定的な盤面生成（初期自動消去を含む、スコア0・アイテム生成なし）
2. マッチ判定（縦横3以上の直線検出）
3. 落下補充処理（重力 + シード値による新タイル供給）
4. 連鎖処理（落下後の再マッチ判定ループ）
5. アイテム生成判定（パターン認識と優先順位）
6. アイテム起動・誘爆処理
7. アイテム合成処理（全パターン）
8. コーヒー×コーヒー全消し時のアイテム残留＋再補充
9. スコア計算（基礎点 × 連鎖倍率 + 同時消しボーナス + 全消しボーナス）
10. ゲーム終了判定（有効スワイプなし かつ アイテムなし）
11. Undo処理（1手前の盤面状態への復元、1プレイ1回制限）

**テスト:** Vitestを用いた単体テスト。各機能に対して正常系・境界値・エッジケースのテストを記述。特にシード値の決定性（同一シード・同一操作で常に同一結果）を検証するテストを必須とする。

### Phase 2: Frontend UI (`frontend/`)

Vue.jsを用いた画面構築。

**実装する画面:**
1. **HOMEダッシュボード:** スタミナ表示、デイリーシードへのショートカット、過去デイリーシードのカレンダーUI、ランキングプレビュー、シード生成ボタン
2. **TODOリスト:** グループ別折りたたみ表示、タスクの作成（タイトル＋任意のメモ・締切日・グループ・繰り返し設定）・完了・削除、サブタスク管理、日次進捗（完了数・アイテム選択権利）表示
3. **パズル画面:** Phase 1のエンジンを組み込み、スワイプ操作・タップ操作・アニメーション・スコア表示を実装。持ち込みアイテムの配置UI、プレイ後のスコア共有・アンロック選択UIを含む。

**技術要件:**
- タッチ操作はVueUseの `usePointerSwipe` を活用
- パズル盤面には `touch-action: none;` を適用
- アニメーションは `transform` ベースで実装
- この段階ではバックエンドはモック（ローカルストレージ等）で代替

### Phase 3: Backend API (`backend/`)

Cloudflare Workers + D1によるAPI実装。

**実装するAPI:**
1. **認証:** 匿名ログイン（UUID→JWT発行）、トークンリフレッシュ
2. **TODO操作:** CRUD、完了処理（スタミナ回復・Undo獲得・日次カウント加算の連動）、繰り返しタスクの再生成、グループ管理
3. **スタミナ管理:** TODO完了による回復（1日5回上限）、時間経過回復
4. **アイテム管理:** TODO進捗に基づくアイテム入手権利判定・選択・ストック管理
5. **Undo管理:** TODO完了による獲得（1日1回、上限10）
6. **パズル・シード管理:** シード生成（ユニーク保証・シリアルコード生成）、デイリーシード取得、過去デイリー一覧（カレンダー用）、共有シードのお試しプレイ、アンロック処理、スコア送信、リプレイ検証（エンジンを用いたサーバーサイド再計算）
7. **共有URL:** `https://tomado.app/s/{seed_id}` エンドポイント。OGPメタタグ生成、アプリ紹介ページ（ストア誘導）の提供
8. **ランキング:** シード値ごとのスコアランキング（持ち込みアイテム使用時は除外）、KVキャッシュ戦略
9. **不正対策:** 全APIエンドポイントへのレートリミット設定

### Phase 4: Native & Monetization

Capacitorによるネイティブビルド設定。

1. Capacitorプロジェクト初期化とiOS/Androidビルド設定
2. `@capacitor/preferences` によるトークン永続化
3. ディープリンク設定（iOS: Universal Links用 `apple-app-site-association` / Android: App Links用 `assetlinks.json` の配置、共有URLからのアプリ内遷移）
4. AdMobプラグイン（広告）の導入
5. In-App Purchase（買い切り広告除去課金）の導入
6. プラットフォーム毎の分岐処理
7. Apple App Attest / Google Play Integrity API によるデバイス認証の導入
